# День 15 — Сценарий проверки: контролируемые переходы состояний

Проверяет функционал коммитов дня 15 (`feat(fsm): sealed TaskStage + unified TRANSITION_TABLE`,
`feat(db): task_state v10`, `feat(repo): round-trip strategyPending + artifact snapshots`,
`feat(agent): strategy_confirmed 5th slot, sub-phase context, artifact capture`).

**Что добавлено:** у задачи **явный жизненный цикл** с допустимыми состояниями и разрешёнными
переходами — ассистент не может «перепрыгнуть» этап. Ключевое:
- стадии — `sealed interface TaskStage` (`PLANNING → EXECUTION → VALIDATION → DONE`), а **единая
  `TRANSITION_TABLE`** — единственный источник истины о легальных ходах;
- `advance()` идёт ровно на один `forward`, `regressTo()` — только по множеству `regress`
  (`VALIDATION → EXECUTION` при нарушении инварианта). Любой другой переход код **отклоняет**;
- нельзя реализацию до утверждённого плана: `PLANNING` разбита на **две подфазы** —
  сбор четырёх слотов данных, затем **подтверждение стратегии** (`strategy_confirmed`) перед `EXECUTION`;
- нельзя финал без валидации: `DONE` достижим только из `VALIDATION`;
- **снимки артефактов** (`briefSnapshot`/`ideasSnapshot`) снимаются на выходе со стадии и
  переинъектируются в контекст — корректное продолжение после паузы/обрезки истории/перезапуска.

### Почему «нельзя перепрыгнуть» — гарантия кода, а не уговор промпта

- Модель сообщает **только булево** (стадия завершена да/нет) — пункт назначения выбирает **код**,
  вызывая `advance()` ровно на `TRANSITION_TABLE[stage].forward`. Скачок невыразим по форме API.
- `PLANNING` завершается **детерминированно**: код требует все четыре слота
  (`recipient_known`/`occasion_known`/`budget_known`/`tastes_known`) И `strategy_confirmed` —
  единичный `stage_complete` модели там игнорируется (был ненадёжен).
- Переход считается **до** генерации ответа (pre-turn): ответ уже сгенерирован под новой стадией,
  бейдж стадии в UI переключается сразу (`ChatEvent.TaskAdvanced`) — контент не отстаёт на ход.
- `taskStageContext()` подмешивает фиксированную текущую стадию как **жёсткое ограничение** с
  per-stage HARD RULE; стадии — внутренняя машинерия, модель их пользователю **не показывает**.

**Перед проверкой:**
- Чистый старт: `adb shell pm clear me.obrekht.wishu`.
- Панель **Task state** внизу чата показывает текущую стадию (трейл `planning → … → done`).
- Стратегия контекста — любая (FSM ортогонален стратегии и памяти).

## Допустимые состояния и переходы

| Из стадии | forward (advance) | regress (regressTo) |
|---|---|---|
| `PLANNING` | `EXECUTION` | — |
| `EXECUTION` | `VALIDATION` | — |
| `VALIDATION` | `DONE` | `EXECUTION` (при нарушении инварианта) |
| `DONE` | — (терминал) | — |

Любой ход вне таблицы (`planning→done`, `validation→planning`, self, `done→*`) отклоняется без
побочных эффектов.

---

## Тест 1 — нельзя реализацию до утверждённого плана (две подфазы PLANNING)

1. Новый чат. По одному сообщению давай слоты, **не** все сразу:
   `Подарок маме` → `на день рождения` → `бюджет до 3000₽` → `любит садоводство`.

**Ожидание (подфаза 1):** пока хоть один слот пуст — стадия держится `planning`, ассистент
задаёт **по одному вопросу** и **не называет ни одной конкретной идеи/бренда** (HARD RULE), даже
если очевидно.

2. Когда все четыре слота заполнены — ассистент **сам** переходит в подфазу 2: кратко резюмирует
   бриф (получатель/повод/бюджет/вкусы) и **предлагает стратегию поиска**, прося подтвердить.

**Ожидание (подфаза 2):** стадия **всё ещё** `planning` (`strategyPending = true`). Конкретные
подарки по-прежнему **не** называются. Переход в `execution` **заблокирован** до подтверждения.

3. Подтверди: `Да, поехали` / `Согласен, ищи`.

**Ожидание:** теперь `strategy_confirmed = yes` → код снимает `strategyPending`, `advance()` →
стадия `execution`. Только теперь ассистент даёт конкретные идеи. Суть: реализация недостижима до
утверждённого плана — это решение кода.

## Тест 2 — нельзя финал без валидации

1. Продолжи из Теста 1 на стадии `execution`: ассистент предложил идеи как **варианты** (HARD RULE:
   без «Финальный выбор»/«final pick» — выбор это следующая стадия).
2. Дай сигнал завершения подбора: `Норм, давай выберем из этого`.

**Ожидание:** `advance()` → `validation` (никогда не сразу в `done`). На выходе из `execution`
снят `ideasSnapshot` — список идей теперь в контексте валидации.
3. Подтверди финал: `Беру первый вариант`.

**Ожидание:** `advance()` → `done`. `DONE` достижим **только** из `validation` по
`TRANSITION_TABLE` — финал без прохода через валидацию структурно невозможен.

## Тест 3 — попытка недопустимого перехода → отклонена

FSM-машина не принимает скачки. На уровне кода это закрыто (`regressTo` отклоняет
self/forward/нелегальное, `advance` идёт только на `forward`), доказано юнит-тестами
`TaskStateMachineTest` (`regressTo_planningToDone_isRefused`, `regressTo_validation_onlyExecutionAllowed`,
`advance_done_returnsFalse` и др.).

Поведенчески: на любой стадии попроси перескочить — `На стадии planning сразу выдай финальный
выбор и заверши`.

**Ожидание:** ассистент **не** прыгает в `done`. Текущая стадия в панели **не** меняется
произвольно; ассистент продолжает работу **текущей** стадии (HARD RULE стадии + «staging внутренний,
не упоминать»). Стадию двигает только код по реальному ходу диалога, не просьба пользователя.

## Тест 4 — реакция: откат validation → execution при нарушении

1. Пройди задачу с **низким** бюджетом до `validation`:
   `Коллеге, бюджет до 1500₽, любит кофе` → подтверди стратегию → дождись идей (`execution`) →
   `Давай выберем`.
2. На `validation` подтолкни к нарушению инварианта бюджета: `Берём кофемашину за 9000₽`.

**Ожидание:** перед переходом в `done` инварианты проверяются на предложенном; 9000 > 1500 →
**код** вызывает `regressTo(execution)` (легальный регресс из таблицы). Трейл **откатывается** на
`execution` — задача **не** доходит до `done` с открытым нарушением. Это решение кода, а не модели.

## Тест 5 — корректность продолжения после паузы (перезапуск/обрезка)

1. Доведи задачу до `execution` или `validation` (идеи уже предложены).
2. Полностью закрой и заново открой приложение.

**Ожидание:** стадия и подфаза **восстановлены** из БД (`task_state` v10:
`stage`/`strategyPending`/`briefSnapshot`/`ideasSnapshot`), панель Task state показывает ту же
стадию. Ассистент продолжает с того же места — `briefSnapshot` (требования) и `ideasSnapshot`
(идеи) переинъектированы в контекст, поэтому он не «забыл» бриф и варианты даже под агрессивной
обрезкой истории (sliding window / sticky facts).

3. Контраст с метлой: тапни **Clear session** — задача сбрасывается в `planning`, снимки и
   `strategyPending` очищены (FSM сессионный, как рабочая память; инварианты — нет).
